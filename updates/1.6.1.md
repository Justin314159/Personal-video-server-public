# 1.6.1

How to install it: [How to update](0-how-to-update.md). Coming from 1.6.0
(or 1.5.0, 1.4.0, 1.3.0), the small `homelib-update.zip` is enough: 1.6.1 uses
exactly the same bundled Python packages.

## What's new

### Every download plays on the iPhone again

Some downloads wouldn't play on the iPhone, neither as video nor in
audio-only mode, even though their thumbnail, details and transcript showed
up fine. The file itself was in a format the iPhone can't play: VP9 or AV1
video, or Opus sound, packed in an mp4.

From now on the app only ever downloads the one combination every iPhone
plays: **H.264 video with AAC (m4a) sound, in an mp4**.

- **Compatible 1080p** works as before, but it no longer falls back to "any
  format" when YouTube's H.264 or AAC streams aren't on offer.
- **Best quality** now means "the highest H.264 version YouTube has" (in
  practice 1080p, sometimes the same as Compatible) instead of 4K VP9/AV1
  that needed VLC.
- If YouTube has no H.264 + AAC version of a video at all (rare), the
  download stops with the message *"YouTube offers no iPhone-compatible
  (H.264 + AAC) version of this video"* instead of saving a file that won't
  play. Tap Retry later, or skip that one.

Music downloads (MP3/M4A) are unchanged; they always played.

## After updating

- **Restart happens by itself** with the update. If you ever update by hand,
  restart the app afterwards (`sudo systemctl restart homelib`) so the new
  download settings are used.
- **Videos you already have aren't changed.** The ones that don't play (the
  player offers "Open in VLC" for them) need downloading again: delete the
  video in the app and download it again, and the new copy is H.264 + AAC.
  You can find them on the server with:
  ```bash
  sudo sqlite3 /var/lib/homelib/homelib.db \
    "SELECT id, vcodec, acodec, title FROM videos WHERE status='ready' AND media='video'
     AND (vcodec NOT LIKE 'avc1%' OR acodec NOT LIKE 'mp4a%');"
  ```
  (`sudo apt install sqlite3` if it's missing.)
- Old behaviour that stays: file names (`<id>.mp4`, Shorts in `shorts/`),
  the Jellyfin files, captions, the database and the config file are as they
  were. A config with `default_quality = "best"` keeps working; it just
  downloads H.264 now.

## Which package

**Small package works** (from 1.6.0, 1.5.0, 1.4.0 or 1.3.0): no bundled Python
package changed.

## Design notes

- **Format strings** (`homelib/formats.py`):
  - `FORMAT_COMPAT = "bv*[vcodec^=avc1][height<=1080]+ba[acodec^=mp4a]/b[vcodec^=avc1][acodec^=mp4a][height<=?1080]/b[ext=mp4][vcodec^=?avc1][acodec^=?mp4a][height<=?1080]"`
  - `FORMAT_BEST` is the same without the height caps.
  - Still `merge_output_format = "mp4"` with `-movflags +faststart`, so a
    merge is a remux (no re-encode).
  - The audio filter is `acodec^=mp4a` (AAC) rather than `ext=m4a`: same
    streams on YouTube, but it also matches AAC that isn't labelled m4a.
  - `^=?` accepts a format whose codec isn't reported. YouTube always
    reports codecs, so this only matters for the plain-mp4 last resort and
    direct-file links (the real yt-dlp pipeline test serves one).
- **Why it broke.** The old Compatible string ended in `/b` (best single
  file, any codec) and Best was `bv*+ba/b`, which with current yt-dlp
  (2026.10.26 in the pins) and YouTube prefers AV1/VP9 + Opus. Whenever the
  H.264/AAC streams weren't offered to yt-dlp's client, or Best was the
  default, the stored mp4 held codecs iOS can't decode, which also breaks the
  player's audio-only mode (same file).
- **Guard.** After a video download `ytlib.download()` checks yt-dlp's
  reported `vcodec`/`acodec` with `formats.ios_playable()`; a known
  non-H.264/HEVC video or non-AAC audio codec deletes the file and fails the
  download (`NO_COMPAT_FORMAT`). yt-dlp's "Requested format is not available"
  is turned into the same message. Unknown codecs pass.
- **"Needs VLC" banner.** `needs_vlc(vcodec, acodec)` is now
  `not ios_playable(...)`, so an old H.264 video with Opus sound also gets the
  "Open in VLC" banner (it listed only the video codec before); the banner
  names both codecs and suggests downloading again.
- **Not touched.** Music options, file naming and placement, the database
  schema (`vcodec`/`acodec` are still stored per video, and `needs_vlc` still
  flags old VP9/AV1 files), the API, the pins.
- **Tests.** `backend/tests/test_formats.py` runs yt-dlp's real format
  selector over fake YouTube format lists (H.264+AAC picked over 4K AV1/VP9;
  360p mp4 when only that is H.264; error rather than VP8/VP9/AV1/Opus) and
  checks `ios_playable()`. `test_ytdlp_pipeline.py` still downloads both
  qualities for real through yt-dlp + ffmpeg.
